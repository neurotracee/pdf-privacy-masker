# 发布 Release 操作指南（网页点击版，不用命令行）

> 这份文件只解决一件事：**把新版本放到 GitHub 的 Releases 页面上，并保证两端「检查更新」能读到。**
> 文中所有 `v<版本号>` 都替换成本次要发的版本（例：`v1.4.6.1`，四段写法）。早期有一个附件叫 `PDF.exe`（旧命名，没版本号、也不是 apk），那种文件名读不出任何版本，所以不会干扰判断。
>
> **这一版有个新东西要先知道**：程序启动会自动检查更新，提醒力度（建议 / 强烈建议）由发布正文第一行的标记决定，两档都能关掉（见第二节「第 4 步 前半」与第八节）。

你已经备好的东西在 `release/<版本号>/`：

| 文件 | 用途 | 大小 |
| --- | --- | --- |
| `PDFPrivacyMasker-<版本号>.exe` | Windows 安装包，**上传** | 约 73 MB |
| `PDFPrivacyMasker-<版本号>-arm64.apk` | 安卓安装包，**上传** | 约 47 MB |
| `RELEASE-NOTES.md` | Release 正文，**复制粘贴** | — |
| `SHA256SUMS.txt` | 校验和，**建议一起上传**，给愿意核对的人用 | — |

`RELEASE-NOTES.md` 不要上传，它是给你复制正文用的。

**上传前至少核对这四项**：exe 的文件属性版本与产品版本都等于本次版本号；两个包的 SHA256 与 `SHA256SUMS.txt` 逐字一致；拿真实文件名试跑版本解析，两个包都能正确读出本次版本号；apk 的签名 SHA1 与上一版一致（不一致就不能覆盖安装）。

---

## 一、先记住顺序：源码在前，Release 在后

Release 的 tag 会指向仓库当时的代码。如果先发 Release、后传源码，`v<版本号>` 这个 tag 指向的还是旧代码，AGPL 要求的“提供能构建出该安装包的完整源码”就不成立。

**所以顺序永远是：先推代码，再发 Release。** 推完确认仓库里的版本号已经变成本次要发的那个，再去建 Release。

判断源码是否到位：打开根目录的 `pdfmask.py`，搜 `VERSION = "`；再打开 `android/app/build.gradle.kts`，搜 `appVersionName = "`（四段写法），两处版本号都与本次发版一致。`versionCode` 不用核对——它由 `appVersionName` 自动算出来。

---

## 二、建 Release（6 步）

全部在浏览器里点。

### 第 1 步 打开新建页

两种入口，效果一样：

- 直接打开：`https://github.com/neurotracee/pdf-privacy-masker/releases/new`
- 或从仓库首页右侧点「Releases」→ 右上角「Draft a new release」

### 第 2 步 填 tag

看到「Choose a tag」按钮，点它，在输入框里敲：

```
v<版本号>
```

下方会出现一条 **「Create new tag: v<版本号> on publish」**，点它选中。
右边「Target」保持 `main` 不动。

> 为什么强调 `v`：程序优先从附件文件名读版本，读不到才退回 tag。tag 不带 `v` 也能认，但仓库里已有的 tag 都带，统一更省事。

### 第 3 步 填标题

「Release title」里填：

```
v<版本号> 这一版最要紧的那件事 · 本次更新：安卓端
```

最后那半句按实际填：**双端** / **仅 Windows** / **仅安卓**。只发一端时，另一端的
检查更新不会动（各端只比自己安装包名里的版本号），所以正文和标题都要写清只影响哪一端，
否则用户会去下载页找一个不存在的包。

### 第 4 步 粘贴正文（第一行决定「建议更新」还是「强烈建议更新」）

用记事本或任意编辑器打开 `release/<版本号>/RELEASE-NOTES.md`，**全选复制**，粘到「Describe this release」大框里。
表格、列表、锚点链接都能正常显示，不用改。

> 正文是**中英双语**：中文在前，第二行是 `**中文** ｜ [English ↓](#english)`。
> 英文版在 `## English` 标题下面，`English ↓` 是页内锚点，点了会直接跳到英文段；英文段顶部的 `[中文 ↑](#中文版)` 跳回中文。
> **一整份一起粘**，不要只粘中文——少了下半段，`English ↓` 就成了死链。

**正文第一行是给程序读的标记：**

```
更新级别：建议
```

- 保持「建议」→ 蓝色提醒，用户点「暂不更新」先被劝一句，再点一次就放行；
- 改成 `更新级别：强烈建议` → 橙红提醒、话更重，挽留也更强，但**照样能关**；
- 整行删掉 → 按「建议」处理。

两档都不拦路：窗口右上角一直有 ×，挽留只有一次，第二次点就一定关得掉。

这一行**必须自己单独占一行、顶格写**。写在表格里、句子中间、或者用代码块包起来都不算——这是故意的，免得正文里举例说明时把所有人误判。

> RELEASE-NOTES 底部有一小段「不要粘」的提示，那一段自己会写明怎么改，粘的时候别把它一起框进去（多粘了也不影响，只是难看）。

**正文里要带三段「安装提示」。** 2026 年 11 月起 OPPO / vivo / 小米 / 荣耀对侧载 apk 做开发者实名校验，本项目没在国内商店上架，装的时候必定弹「开发者身份未验证」。发布页是用户下载前一定看得到的地方，正文开头必须写清三件事：

1. **为什么会提示「开发者身份未验证」**——作者未成年，ADV 需要本人身份证、本人实名银行卡与人脸活体，这一关过不去；提示只是提醒，勾选「已知悉应用风险」→「仍然安装」即可；
2. **为什么提示「信息将被第三方收集」**——系统安装器对所有非商店包的模板文案，本程序没有第三方 SDK；
3. **唯一联网行为**——自动/手动检查更新，只连 Gitee 与 GitHub 两个仓库，不上传任何东西。

应用内的更新弹窗也会显示同样的安装提示（`ui/UpdateNotes.kt` 的 `InstallHint()`），两处都要有，缺一处就会有用户以为包坏了。`release/<版本号>/RELEASE-NOTES.md` 的模板已经包含这三段，照抄即可。

### 第 5 步 传附件（最容易出错的一步）

找到「Attach binaries by dropping them here or selecting them」那块区域：

1. 打开打包目录下本次的 `release/<版本号>/` 文件夹
2. 选中 `PDFPrivacyMasker-<版本号>.exe` 和 `PDFPrivacyMasker-<版本号>-arm64.apk` 两个文件
3. 直接拖进那块区域（或点「selecting them」选这两个文件）
4. 等进度条走完，两个文件名出现在下方列表里

传完必须**逐字核对文件名**，这三个特征一个都不能少：

| 必须有 | 为什么 |
| --- | --- |
| 前缀 `PDFPrivacyMasker-` | 程序靠这个前缀 + 后缀来认定"这是本平台的包" |
| 中间 `<版本号>` | **版本号就是从这里读的**，没有它就会退回读 tag |
| exe 结尾 `.exe`、apk 结尾 `-arm64.apk` | Windows 只认 `.exe`，安卓只认 `.apk` |

**不要**用中文名（`PDF隐私打码工具.exe`）、不要带空格、不要写成 `PDFPrivacyMasker-1.4.exe` 这种缺位的版本号（会被读错）。

`SHA256SUMS.txt` 想传就一起传，不传不影响任何功能。

### 第 6 步 检查两个勾选框，然后发布

页面底部有两个勾：

- **「Set as a pre-release」** —— **不要勾**
- **「Set as the latest release」** —— 保持默认（勾着就对）
- 「Save as draft」不要点

然后点绿色 **「Publish release」**。

> 为什么不能勾 pre-release：程序的检查更新会跳过草稿、但**不跳过**预发布；可「打开下载页」用的是 `/releases/latest`，GitHub 不把 pre-release 算作 latest，会把用户送到 v1.3.0 去。结果就是"提示有新版本，点开却下到旧版"。所以别勾。

## 三、发完当场自检（3 分钟）

### 检查 1：看接口里有没有本次的两个包

浏览器打开：

```
https://api.github.com/repos/neurotracee/pdf-privacy-masker/releases
```

在最上面那一坨里找 `"tag_name": "v<版本号>"`，然后往下找 `"name":`，应该出现：

```
"name": "PDFPrivacyMasker-<版本号>.exe"
"name": "PDFPrivacyMasker-<版本号>-arm64.apk"
```

两个都在，且 `"draft": false`、`"prerelease": false`，就对了。

### 检查 2：下载页要落在本次版本

打开 `https://github.com/neurotracee/pdf-privacy-masker/releases/latest`，地址栏应该自动变成 `.../releases/tag/v<版本号>`。
如果还停在 `v1.3.0`，说明第 6 步勾了 pre-release，回去编辑取消。

### 检查 3：两端真点一次「检查更新」

- Windows：打开新 exe → 右上角「设置」→「版本与更新」→「检查更新」。当前版本应等于本次发版版本，应该显示"已是最新版本"。
- 安卓：装本次版本 → 设置 →「版本与更新」→「检查更新」，同样显示已是最新。

这一步的真正意义是**反向验证命名对不对**：如果 Windows 报"仓库里还没有适用于本平台的安装包"，就是 exe 名字里没有被认出的版本；如果显示"发现新版本 1.3.0"，就是附件名解析乱了。

## 四、发布后想改什么，怎么改

| 想改 | 怎么做 |
| --- | --- |
| 正文写错了 | Releases 页面右上「编辑」铅笔图标 → 改正文 → 「Update release」。不用重新传包 |
| 附件传错了 / 想换 | 编辑页面附件右上角有删除（垃圾桶）图标，删掉再拖新的进去。**删了旧附件，旧直链会 404**，但检查更新走接口、不受影响 |
| 忘了传 apk | 编辑页面同一处继续上传即可，不用重新发版 |
| tag 写成了 `v1.4` | 只能删掉整个 Release 重建（tag 会跟着删）。所以第 2 步慢一点 |
| 想撤回整版 | 编辑页面底部「Delete this release」。tag 会留着，需要另外去 Tags 里删 |

---

## 五、老 v1.3.0 那个 `PDF.exe` 要不要改名

**结论：不用改，也别改。**

理由：

1. 程序读版本时按"文件名里有没有版本号"过滤，`PDF.exe` 里读不出 `x.y.z.w`，会被直接跳过，不会盖住新版本。
2. 那个文件名是当初分享出去的，可能已经有人在用直链下载；改名会让旧链接 404。
3. 它在页面上留着反而是历史记录，v1.3.0 的正文里也写着这个文件名。

以后每一版都按 `PDFPrivacyMasker-<版本>.exe` / `PDFPrivacyMasker-<版本>-arm64.apk` 命名就不会再出现这个问题。规则已写进 `docs/05-构建与发布.md` 第 4.1 节。

## 六、发版时到底要传哪些文件

代码现在是用 git 推的，`git push` 一次就把所有改动带上去了，**不需要在网上一个个点**。

如果哪次必须在网页上手动传（换了电脑、手边没有 git），判断方法很简单：以本地仓库为准，把 `git status` 里有改动的文件全传一遍。手写清单一定会漏——本节早期版本就列过一份「本次要传的文件」，两版之后就完全对不上了，所以删掉了。

只有一类文件在网页上要格外注意：`.github/workflows/` 里的工作流。GitHub 要求令牌带 `workflow` 权限才能推，没有这个权限时只能网页新建。

**千万别传**：`release/`、`dist/`、`build/`、`android/app/build/`、`android/keystore.properties`、`*.jks`、`local.properties`、`dev/_ui/`。要么是产物、要么是密钥，`.gitignore` 已经拦了，但手动拖拽能绕过去，上传时看清文件名。

---

## 七、哪些东西不能进仓库

`.gitignore` 已经挡住了打包产物和密钥。手动拖拽上传不受它约束，所以列一下，上传时留个心：

| 路径 | 为什么不传 |
| --- | --- |
| `release/`、`dist/` | 安装包与打包中间产物，体积大；发布走 Release 附件 |
| `build/`、`android/app/build/`、`__pycache__/` | 编译缓存，能重新生成 |
| `android/keystore.properties`、`*.jks` | **签名密钥，泄露等于别人能冒充你发安装包** |
| `local.properties` | 本机 SDK 路径，换台机器就不对了 |

`test/` 是例外，它**应该**在仓库里——`dev/selfcheck.py` 要用这几个 PDF 跑端到端检查。里面都是自己造的样例，不含任何真实个人信息。

---

## 八、以后每次发版，只要三步

1. 改三处版本号：`pdfmask.py` 的 `VERSION`、`version_info.txt` 两处、`android/app/build.gradle.kts` 的 `appVersionName`（安卓的 `versionCode` 会自动算出来，不用手填）。版本号写四段，例 `1.4.6.1`。
2. 打包，把产物按 `PDFPrivacyMasker-<新版本>.exe`、`PDFPrivacyMasker-<新版本>-arm64.apk` 命名，放到 `release/<新版本>/`。
3. 回到本文第二节，把文中的 `v<版本号>` 全部替换成新版本号，正文换成 `CHANGELOG.md` 新增的那一节——**别忘了第一行那句「更新级别：建议」**，删掉它等于按建议处理；想让提醒更重就写成 `更新级别：强烈建议`，但两档都关得掉。

> 小抄：想让某一版提醒更重，就把正文第一行改成 `更新级别：强烈建议`，别的话照常写。发完拿旧版打开一次：徽标是橙红色、标题是「强烈建议更新到 vX」，点「暂不更新」会多问一句——就是读到了；如果还是普通蓝标，说明那一行没顶格或被包进了代码块。

`CHANGELOG.md` 只往后加新节，**不要改旧节**——旧节对应的是别人已经下载过的版本，改了就对不上了。
